# v0.3 improvement plan

Implementation spec for the next release. Each section is one pull request, in the order listed. Every file, function and flag named here was read in the repository on 2026-10-30. Anything marked **VERIFY** depends on an outside fact that was not confirmed; check the official source before writing code for it, and record the URL and date in the PR description.

## Why this release

v0.1.0 and v0.2.0 built the features. Nothing yet shows they work for a buyer:

- The 13 cases in `evals/evals.json` have never been run.
- The floor-plan tools have not been tried on a real plan (see `docs/release-notes.md`, "Limits").
- The README says "download the zips from the latest release", but the v0.2.0 release has no files attached.
- 32 dated facts sit in skills and scripts. Only `trades.py` warns when its rules are old (`STALE_DAYS = 180`). The NYC tax rates in `cash_to_close.py` are hard-coded with "checked 2026-09" and never warn.
- `nyc_records.py` and `us_flood.py` have no tests, and `nyc_records.py` has correctness bugs (PR 3).

The project's promise is trust. So this release makes the existing work correct, fresh and measurable, and adds no new features beyond a way for the buyer to correct the floor-plan scale.

## Decisions already made

| Question | Decision | Reason |
|---|---|---|
| Which agents | Claude Code and Codex first. Gemini CLI and Cursor when their CLIs are installed | Users pick their own AI. The skills already use the portable `SKILL.md` format, so the work is in testing and install docs |
| Eval cost | Run on the user's subscription logins (`claude -p`, `codex exec`), save tokens: cache by content hash, baseline run once, deterministic checks before any model grading, one grading call per case, never in CI | No API budget |
| Floor-plan validation | No ground-truth study. Instead let the buyer enter tape measurements, rescale the plan from them, and flag plans that are distorted rather than mis-scaled | No real measured plans are available |
| README "Why this isn't a black box" | Keep it and drop the shorter paragraph it repeated | Its claims were checked against the code and it says more |
| Second jurisdiction, new floor-plan features | Out of scope for v0.3 | Each new location adds more dated facts. Build PR 5 first |

## Rules for every PR

- Python standard library only. Python 3.9 is the floor (the lowest version in `.github/workflows/test.yml`).
- Match the existing style: short functions, plain names, comments only where the reason is not obvious.
- Repository writing rules apply to every text file, including this one: English, plain words, no em dashes, no emoji. `tools/check_skills.py` enforces this.
- Never put real private people, owners or addresses in fixtures or examples. API fixtures must be made up by hand, not copied from live responses: live NYC responses contain real owner names (PLUTO `ownername`, ACRIS parties).
- Before opening each PR, both of these must pass:

  ```bash
  python3 -m unittest discover tests
  python3 tools/check_skills.py
  ```
- One branch per PR. Do not combine PRs.

## PR 3. Public-records scripts: fix bugs, add tests, weekly live check

**Why:** These scripts produce the "anything wrong with this house" facts. A silent wrong answer here is the most expensive failure in the project, and rule 2 ("zero rows is not clean") depends on the script being honest about what it did not fetch.

### 3a. Bugs in `skills/house-records/scripts/nyc_records.py`

| # | Where | Problem | Fix |
|---|---|---|---|
| 1 | `run()`, `dob_complaints` | `'$order': 'date_entered'` sorts oldest first with `'$limit': 100`. A building with more than 100 complaints shows the oldest 100 and hides the newest | `'$order': 'date_entered DESC'` |
| 2 | `run()`, ACRIS | Document IDs are deduplicated, sorted as strings and cut to `ids[:150]`. For a lot with more than 150 documents, the details fetched are an arbitrary subset by ID, not the newest | Fetch details in batches of 150 IDs until all IDs are covered (at most 500, see #3). Merge the results and sort by `document_date` descending |
| 3 | `run()`, every `'$limit'` query | When a query returns exactly its limit (ACRIS legals 500, BIS jobs 50, DOB NOW jobs 50, COs 50, complaints 100, 311 groups 30), more rows may exist and the output does not say so | Add `out['truncated'] = [names]` for every query that hit its limit. `show()` prints `showing the first N; more exist, see the source` beside that section |
| 4 | `run()`, `count()` | A failed count returns the error string, and `show()` prints it in the number column (`DOB violations   URLError: ...`) | `show()` prints `query failed: <error>` when the value is not an int |
| 5 | `main()` | `--bbl` and `--bin` are not validated. A short BBL makes `split_bbl` slice wrong values, and the values are pasted into SoQL `$where` strings | Require `--bbl` to match `^[1-5]\d{9}$` and `--bin` to match `^\d{7}$`. Otherwise call `ap.error(...)` |
| 6 | `candidates()`, `get()` | A network failure in Geosearch raises a traceback | Catch `urllib.error.URLError`, `TimeoutError` and `json.JSONDecodeError` (a `ValueError`) in `main()` around `candidates()`, and exit with `sys.exit('Geosearch failed: ...')`. `soc()` already catches its own errors |

### 3b. Bugs in `skills/house-records/scripts/us_flood.py`

| # | Problem | Fix |
|---|---|---|
| 1 | Network failure in `geocode()` or `flood_zone()` raises a traceback | Catch the same errors as 3a #6 and exit with a one-line message naming which service failed |
| 2 | With `--json`, a FEMA error exits 0. Without `--json` it exits 1 | Exit 1 in both cases after printing the JSON |

## PR 5. One list of every dated fact, with age checks

**Why:** Ground rule 10 says to re-check time-sensitive facts, but only `trades.py` enforces it. Rates, tax brackets, dataset IDs and code sections in prose go stale without anyone noticing.

### New `tools/facts.json`

```json
{
  "schema": "housingwizard.facts/1",
  "facts": [
    {
      "id": "nyc-mansion-tax-brackets",
      "file": "skills/house-money/scripts/cash_to_close.py",
      "match": "NYC_MANSION = [",
      "what": "NYS mansion tax brackets for NYC purchases",
      "source_url": "https://...",
      "checked": "2026-09-01",
      "max_age_days": 180,
      "kind": "tax"
    }
  ]
}
```

- `match` is an exact substring that must appear in `file`, so the entry fails if the fact is moved or deleted.
- `kind` is one of `tax`, `rate`, `fee`, `code`, `dataset`, `process`. Default `max_age_days`: `rate` 30, `tax` and `fee` 180, `code` 180, `dataset` 365, `process` 365.
- `rules/us-ny-nyc.json` already carries its own dates. Add one entry pointing at that file, and let `trades.py` keep owning the per-rule staleness.

### Inventory step

Find every dated or time-sensitive fact with:

```bash
grep -rnE "(checked|read|as of)[^.]{0,20}20[0-9]{2}" skills
```

The 2026-10-30 count was 32 matches in `house-contract/references/new-york.md`, `house-floorplan/references/costbook.md`, `house-floorplan/rules/us-ny-nyc.json`, `house-money/scripts/cash_to_close.py` and `house-records/references/nyc.md`.

Then read each of these files for undated facts that change over time (rates, fees, dollar thresholds, dataset IDs, form numbers) and add entries for them too. Where a fact has no date in the text, use the date of the git commit that introduced it (`git log --format=%ad --date=short -S '<text>' -- <file> | tail -1`) as `checked`, and say in the PR that this date is "added on", not "checked on".

### New `tools/check_freshness.py`

- Validates the structure: required keys, ISO date, known `kind`, the file exists, `match` is found in the file.
- Reports each fact's age against `--today` (default today).
- Exit codes: 0 when all facts are fresh, 1 on a structural error, 2 when any fact is stale.
- `--json` for machine output.

### Wiring

- `tools/check_skills.py` calls `check_freshness.py --structure-only`, so a moved or deleted fact fails PR checks, but the passing of calendar time never turns a PR red.
- `.github/workflows/live-records.yml` (from PR 3) gets a second job that runs `python tools/check_freshness.py` weekly. A stale fact fails the scheduled run and emails the owner.
- `CONTRIBUTING.md`, "Add a location": every new local rule needs a `tools/facts.json` entry.

**Tests:** new `tests/test_freshness.py`, using temp files:
- a fresh fact passes;
- a stale fact exits 2;
- a missing `match` exits 1;
- the real `tools/facts.json` passes `--structure-only`.

**Binaries:** `--claude-bin` (default `claude`) and `--codex-bin` (default `codex`). Shell aliases are not visible to `subprocess`, so the owner may need `--codex-bin codex-tech` or a full path.

**Gemini CLI and Cursor:** add adapter stubs that exit with "not installed or not yet supported". Implement them only after installing the CLI and reading its help. Do not guess flags.

### Token saving

- **Cache.** The key is the SHA-256 of: the agent name, the model if given, the case's `prompt`, every file under `skills/<case skill>/`, every file under `skills/house-buying/` (the router), and `tools/shared_rules.md`. A cached result is reused and not rerun.
- **Baseline.** Without skills, results are computed only with `--baseline` and are cached forever, until `--refresh-baseline`.
- **Selection.** `--case ID[,ID]`, `--skill NAME` and `--changed` (only cases whose cache key changed since the last committed results).
- **Grading.** First run `checks`. If every assertion is covered by checks, no model is called. Otherwise make one grader call per case covering all remaining assertions, using `claude -p --model <judge> --output-format json`, with `--judge-model` defaulting to `sonnet`. The prompt asks for strict JSON: `[{"assertion": "...", "pass": true, "quote": "..."}]`. On a parse failure, retry once, then mark the case `grader_error`. Do not loop.
- **Paid-key guard.** Refuse to start if `ANTHROPIC_API_KEY` or `OPENAI_API_KEY` is set, unless `--allow-api-key` is passed. Those variables can switch the CLIs from subscription use to billed API use.
- **Dry run.** `--dry-run` prints which cases would run and how many agent and grader calls that means, then exits.
- **Never in CI.**

### Output

- `evals/results/<agent>.json`: per case, with skills and baseline: answer text, check results, assertion results, cache key, date, CLI version (`--version` output).
- `evals/results/summary.md`: a table of case, skill, with-skills passed out of total, baseline passed out of total, and a total row per agent. Regenerated on every run.
- Add a "Results" section to `README.md` linking to `summary.md` once the first real run exists. Do not write numbers into the README by hand.

## PR 7. Floor plan: correct the scale from tape measurements

**Why:** Listing plans are often drawn at a slightly wrong scale, and sometimes drawn out of proportion. The buyer cannot get a measured survey, but can measure one or two rooms on a visit. Everything downstream (quantities, costs, packages) should follow from those measurements, and the tool should say when a single scale factor cannot fix the plan.

### Background (verified in code)

- Plan coordinates are in plan units (`ft` or `m`), not pixels.
- The overlay places a point at `image_origin_px + coord * source.scale_px_per_unit` (`assets/viewer.html`, `const S = (D.plan.source||{}).scale_px_per_unit || 10`).
- So multiplying every coordinate by `k` and dividing `scale_px_per_unit` by `k` leaves every overlay pixel exactly where it was. A uniform rescale does not change the confirmed transcription, so `source.overlay_confirmed` stays valid. Any other geometry change still needs a new confirmation, as `references/schema.md` already says.

### Schema addition (`references/schema.md`): `source.measurements[]`

```json
{"id": "m1", "ref": {"floor": "1F", "room": "LR", "axis": "x"}, "value": 14.17, "by": "Buyer", "on": "2026-11-02", "note": "wall to wall at waist height"}
{"id": "m2", "ref": {"floor": "1F", "wall": "w1"}, "value": 28.1, "by": "Buyer", "on": "2026-11-02", "note": "outside, corner to corner"}
```

- A room reference measures the room polygon's bounding-box extent along `axis` (`x` or `y`). Room polygons are interior, matching how `label_dims` are read.
- A wall reference measures `plan_tools.wall_len(w)`.
- `value` is in the plan's units.
- Heights are not measurements here. They already have `floors[].height` with `height_source: "measured"`.

### `plan_tools.py`: new `measurement_report(plan)`

For each measurement: `plan_len`, `k = value / plan_len`, and its deviation from the median `k`. Overall:
- `factor` is the median `k`;
- `spread` is `max(k) / min(k) - 1`;
- `status` is one of:
  - `none`: no measurements;
  - `single`: one measurement, so the scale is set but not cross-checked;
  - `consistent`: two or more, spread at most `MEASURE_SPREAD = 0.03`, labeled as an assumption in a comment, the same way `STALE_DAYS` is;
  - `distorted`: two or more, spread above 0.03.

`validate()` adds these errors and warnings:
- error: an unknown floor, room or wall reference, or a non-positive value;
- warning: `distorted`, naming the measurements furthest from the median;
- warning: `|factor - 1| > 0.02`, meaning the plan is off scale and `rescale_plan.py` should be run.

### New `scripts/rescale_plan.py`

```bash
python3 rescale_plan.py plan.json --out plan.rescaled.json [--changes changes.json --changes-out changes.rescaled.json] [--factor K]
```

- With no `--factor`, it uses `measurement_report(plan).factor` and refuses unless `status` is `single` or `consistent`. A `distorted` plan is refused with the list of rooms and walls that disagree, because no single factor fixes a plan drawn out of proportion. The fix is re-transcribing those rooms, which needs a new overlay check.
- **Multiplied by k:** wall `a` and `b`, room `poly`, stair `poly`, fixture `at` and `size`, `unknown[].poly`, and opening `offset` and `width`. In `changes.json`, every coordinate and length field of the same kinds, so a proposal drawn at the old scale still lines up.
- **Not changed:** wall `thick`, which is nominal and typed in rather than measured off the plan; `height`, `elevation`, `sill` and `head`, which are vertical and not set by the plan scale; `image_origin_px`; and `declared_area`.
- **Bookkeeping:**
  - set `source.scale_px_per_unit` to the old value divided by `k`;
  - record `source.rescaled = {"factor": k, "from": [ids], "on": "YYYY-MM-DD"}`;
  - keep `source.overlay_confirmed` as it is;
  - append to `source.scale_from`: `"; rescaled by <k> from measurements <ids>"`;
  - after rescaling, update each measurement's implied `k` to 1.
- It never edits the input file in place.

### `takeoff.py`

- `_soft_scale(plan)`: a `consistent` measurement report satisfies both the `scale_from` and the `scale_check` reasons; `single` satisfies only `scale_from`. `distorted` adds the reason `measurements disagree by <spread>%; quantities in rooms <list> are unreliable`.
- `scale_source` becomes `measured (<ids>)` when the plan was rescaled from measurements.
- New top-level `measure_next` in `takeoff.json`: up to three rooms that carry the largest share of total floor area, each with the longer axis to measure. Skip it when status is `consistent`. Floor area is used rather than cost so that this works without a price book.

### Viewer and docs
